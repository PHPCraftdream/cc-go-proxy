# Fast mode protocol evidence

Research snapshot: 2026-11-18. This is evidence for a translation design, not a claim that either provider guarantees equivalent latency, billing, availability, or model quality. No provider sessions or inference calls were made.

## Anthropic: selection is not capability

- Claude Code documents `/fast` as a user toggle and `fastMode` as a saved client setting. It also describes client-side availability checks and model restrictions. Neither a model's ability to run fast nor a successful availability check says that this particular request selected fast. See [Claude Code fast mode](https://code.claude.com/docs/en/fast-mode#toggle-fast-mode) and [gateway checks](https://code.claude.com/docs/en/fast-mode#use-fast-mode-behind-proxies-and-llm-gateways) (living documentation).
- The [Messages API fast-mode documentation](https://platform.claude.com/docs/en/build-with-claude/fast-mode#basic-usage) specifies the **top-level request body** `"speed":"fast"` for opting in. The [pinned official TypeScript SDK](https://github.com/anthropics/anthropic-sdk-typescript/blob/3f13f60335f8bcf91a782785f4f16e4267c999ad/src/resources/messages/messages.ts#L7750-L7758) declares `speed?: 'standard' | 'fast' | null`. A fast-mode beta header can be required for certain models, but a header announcing feature support is not itself the per-request selection. No inference from the model name, beta header, or client setting alone is justified.
- The [API documentation](https://platform.claude.com/docs/en/build-with-claude/fast-mode#checking-which-speed-was-used) identifies response `usage.speed` as the speed actually used, which is distinct from the requested speed; it documents an exception where a fast request runs standard. Do not synthesize confirmation of actual speed merely from the request. Microsoft Foundry uses a different model/deployment convention; this note concerns the Anthropic-shaped Messages request, not that provider's deployment protocol.
- Claude Code's public documentation establishes the toggle and the Messages API contract, but does not by itself prove the precise bytes emitted by every Claude Code version, provider configuration, or gateway. In particular, it does not establish that a beta header alone means `/fast` is enabled. Capture-free fixture tests can validate the documented API shape; a version-specific client trace would need separate evidence.

## OpenAI Codex: catalog label versus wire ID

All Codex source links below are pinned to public commit [`6d9f0199ed0cfdd184754e593e0625917ad0ca28`](https://github.com/openai/codex/commit/6d9f0199ed0cfdd184754e593e0625917ad0ca28).

- The [bundled model catalog](https://github.com/openai/codex/blob/6d9f0199ed0cfdd184754e593e0625917ad0ca28/codex-rs/models-manager/models.json) includes, for example, model `gpt-6.2-sol` with `service_tiers: [{"id":"priority","name":"Fast","description":"2x speed, increased usage"}]` and separately `additional_speed_tiers: ["fast"]`. These are different fields and vocabularies: `Fast` is a display name, `priority` is the tier ID, and `fast` is an additional speed-tier capability. Model entries vary; do not assume every model offers it or hard-code the example as a current live catalog.
- The [Codex tier UI](https://github.com/openai/codex/blob/6d9f0199ed0cfdd184754e593e0625917ad0ca28/codex-rs/tui/src/chatwidget/service_tiers.rs) finds the fast option by name and applies its **catalog ID**. The [tier resolution](https://github.com/openai/codex/blob/6d9f0199ed0cfdd184754e593e0625917ad0ca28/codex-rs/tui/src/service_tier_resolution.rs) validates a configured choice against known model tiers; unsupported selections do not automatically become the model default. Feature flags and defaults also affect selection.
- The [Codex Responses request construction](https://github.com/openai/codex/blob/6d9f0199ed0cfdd184754e593e0625917ad0ca28/codex-rs/core/src/client.rs#L1305-L1334) resolves `service_tier` against model information and puts it into `ResponsesApiRequest` alongside `model`. For the cited catalog entry, the source-supported selection is `"service_tier":"priority"`, not `"service_tier":"fast"`; the latter is not established by the `additional_speed_tiers` field. Codex has provider-specific handling, including a Bedrock advertised-tier filter, so do not generalize every path to OAuth.
- These sources establish the official client's catalog and request construction, not an independent guarantee that the ChatGPT OAuth backend accepts a tier for every account/model, or that its live catalog matches the bundled snapshot. Account entitlements, server-provided catalog overrides, errors, actual service tier and fallback behavior need separate evidence. Do not silently claim a fast response or assume a paid-tier fallback policy from this mapping.

## Fixture-based checks

Use synthetic, public-data-only fixtures; no credentials, tokens, private transcripts, or live calls.

1. Feed otherwise identical Messages bodies with `speed: "fast"`, `speed: "standard"`, omitted `speed`, and `speed: null`. Only the explicit fast value is a fast request; define and test the application's policy for absent, null, and unknown values without interpreting them as fast.
2. A body with no fast selection plus a fast-mode beta header, supported-model name, or mocked capability must not be promoted to fast. Conversely, an explicit fast selection must not depend solely on presence of a beta header: requirements vary by model and API version.
3. Model catalog fixture: `{"slug":"gpt-6.2-sol","service_tiers":[{"id":"priority","name":"Fast","description":"2x speed, increased usage"}],"additional_speed_tiers":["fast"]}`. Assert selected `Fast` resolves to ID `priority` and that a translated Responses body uses `service_tier: "priority"`, not `"fast"`. This is a candidate translation policy based on two client contracts, not an Anthropic- or OpenAI-specified cross-provider mapping.
4. Fixture a model without the tier and an unknown model; assert no unsupported fast-tier inference. Test catalog IDs independently of labels, and do not assume `additional_speed_tiers` by itself selects a tier. If the application chooses rejection or an explicit fallback, test that policy rather than inventing a provider guarantee.
5. Cover response `usage.speed` separately from input selection, including an upstream failure or unknown actual speed; do not mark speed as confirmed fast without evidence. Verify both streaming and non-streaming request construction if the implementation supports both.
